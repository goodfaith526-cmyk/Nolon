## 2. ثغرات عامة (تمس مناطق كثيرة)

### ع1. التعديل المتزامن على الشاشات العادية: آخر حفظ يمسح ما قبله (صنف 7) ⚠️

مسودات المساعد لها `version`، والعميل له فحص "النموذج القديم" (`customers.service.ts:283`). باقي شاشات التعديل
(مسودة الفاتورة، عرض السعر، مسودة الحجز، كرت السعر، بيانات الشحنة، ملف الجمارك، مسودة فاتورة المورد، القيد اليدوي)
تحفظ بلا فحص: موظفان فتحا نفس المسودة، الثاني يحفظ فوق الأول بلا تنبيه (`invoices.service.ts:919`،
`customs.service.ts:151`، `shipments.service.ts:477`). لا يفسد الحسابات (الاعتماد يقفل الصف)، لكن يضيع عمل موظف.

### ع2. الإرسال المكرر يسجل العملية مرتين (صنف 7) ❌ للسند، ⚠️ للباقي

زر الحفظ يُعطَّل أثناء الطلب، وهذا يمنع الضغطتين فقط. إعادة الإرسال بعد انقطاع الشبكة، أو تبويبان مفتوحان، تُنشئ
سجلين. المصروف وفاتورة المورد والسداد وإشعار الدائن والأرصدة الافتتاحية لها `requestId` يمنع هذا. **سند القبض لا**
(`billing.controller.ts:84`، `createReceiptBody` بلا `requestId`): سند مكرر = قيد نقدية مكرر. ومثله بلا حماية:
استلام GRN، الإفراج، الـ POD، إنشاء الحجز والعرض والرحلة والحاوية. (الـ GRN المكرر الكامل يوقفه فحص الطرود الزائدة؛
الجزئي المكرر يمر.)

### ع3. التواريخ: العمليات محمية، المالية لا (صنف 6) ❌

- العمليات (حالة الشحنة، الحاوية، الرحلة، المستودع، الـ POD، الجمارك) ترفض المستقبل (`FUTURE_TOLERANCE_MS`).
- **المالية لا ترفض المستقبل**: تاريخ الفاتورة والسند والمصروف وفاتورة المورد والسداد والقيد اليدوي (`dateString` فقط في
  الـ controllers). خطأ كتابة سنة (2062 بدل 2026) يفتح فترة في المستقبل، ويخرّب أعمار الديون وتقرير الاستحقاق.
- حد أدنى ناقص: سند قبض بتاريخ قبل الفاتورة التي يسددها (التطبيق اللاحق يفحصه في
  `receipt-application-rules.ts:78`، التوزيع عند الإنشاء لا)، وسداد مورد قبل تاريخ فاتورته
  (`supplier-payments.service.ts:139`).
- استلام GRN بوقت قديم يحرك الشحنة بلا فحص "قبل آخر حالة" (`warehouse-movements.service.ts:277`؛ الجمارك تستخدم
  `beforeLatestEvent`، المستودع لا). نفس عائلة #109 أ.

### ع4. السجلات التشغيلية بلا طريق تصحيح (صنف 8) ❌

خطأ يكتشفه الموظف بعد الحفظ، ولا يوجد له في الـ API إلا الإلغاء الكامل للشحنة:

| السجل                        | ما يحدث اليوم                                                           |
| ---------------------------- | ----------------------------------------------------------------------- |
| استلام GRN / إفراج           | لا إلغاء ولا تصحيح (لا route). كمية أو مخزن خطأ يبقى للأبد              |
| الـ POD                      | لا إلغاء. POD على الشحنة الخطأ يبقى                                     |
| الرحلة بعد "غادرت"           | لا رجوع، ولا إخراج شحنة منها (`trips.service.ts:385`: قبل المغادرة فقط) |
| الحاوية بعد "أُقفلت"         | لا إعادة فتح، ولا إخراج شحنة (`consolidation-rules.ts:17`)              |
| بنود البضاعة بعد تأكيد الحجز | لا تعديل للوزن والحجم والطرود (`ShipmentUpdateRequest` بلا بنود)        |

أخطرها الأخير: حجز LCL تأكد بلا CBM لا يمكن إقفال حاويته (`freezeBasis` يطلب CBM، ولا شاشة تسمح بإدخاله)، والحل
الوحيد إخراج الشحنة من الحاوية. وتكلفة الحاوية تتوزع على الحجم المحجوز لا المقاس فعلاً.

- **ق3** فاتورة ثانية لنفس الشحنة: **نبّه وتأكيد ⭐** / ارفض / اتركه.
- **ق4** التاريخ المالي في المستقبل: **ارفض بعد اليوم ⭐** / اسمح حتى 30 يوماً.
- **ق5** سعر الصرف القديم: **نبّه إذا أقدم من 7 أيام ⭐** / ارفض بعد 30 يوماً / اتركه.
- **ق6** حد الائتمان: **نبّه في الحجز والفاتورة ⭐** / امنع / اتركه معلومة فقط.
- **ق7** طرق التصحيح في ب3: **كلها ⭐** / GRN والـ POD وبنود البضاعة فقط / لاحقاً.

## 6. أثر الوكيل

- ب1: الوكيل لا يلغي الحجوزات ولا الشحنات. تنبيه الفاتورة الثانية يُضاف كحقل جديد في `/invoice-drafts/suggest` (إضافة،
  لا تغيير شكل). `requestId` لـ `POST /receipts` لا يمس الوكيل (مسودات السند لها مفتاحها).
- ب4: حد التاريخ المستقبلي يمس مسودات الفاتورة والسند عند الاعتماد: رفض جديد بكود جديد. يحتاج ملاحظة لمشروع الوكيل،
  لا PR توافق، لأن الوكيل يقترح تاريخ اليوم.
- ب2، ب3، ب5، ب6: شاشات وروابط بشرية؛ لا مساس بأدوات الوكيل. إن أُضيف تعديل بنود البضاعة كمسار مسودة لاحقاً،
  يمر بفحص الأثر.
