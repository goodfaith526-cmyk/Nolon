# قراءة الملف الحالي لصاحب هوية القناة

امتداد مرشح للمراجعة لعقد `nolon.customer-identity/1` فوق تنفيذ #155 على `d356c6e`، وليس نشراً أو إذناً
بالتفعيل. لا هجرات أو أسرار أو صلاحيات جديدة، ولا تغيير في ضمانات الكتابة أو نسخ نتائج العمليات الأصلية.

## الطلب

`GET /api/v1/cs/customer-profiles/self?conversationId=...`

المفتاح نفسه ذو `cs:customer_profiles:write` والغلاف الموقّع الموثوق؛ الميزة الأساسية يجب أن تكون مفتوحة
بتكليف منفصل. لا يحتاج مفتاح المتابعة أو الحجز لكي يقرأ الحالة الموجودة. لا يعتمد على اسم عرض القناة أو
username أو هاتف مكتوب. Query صارم: `conversationId` غير فارغ حتى 128 حرفاً فقط. لا `profileId` أو
`customerId` أو `companyId` أو اختيار مرسل من النموذج. لا body ولا Idempotency-Key مطلوبين للقراءة.

التوقيع كما في العقد الأصلي: method=`GET`، المسار مع query المرتّب والمشفّر بـ URLSearchParams، سطر
Idempotency-Key فارغ، وبصمة body الفارغ. حقل conversationId في query مشمول بالتوقيع. المرجع القابل للاختبار
في `08d-customer-profile-self-examples.json`، مع أمثلة الرد الكامل والقيم والمطابقة الملتبسة.

## حسم الهوية والاتساق

تستنتج نولون الملف من `(الشركة المضبوطة، المفتاح، conversationId)` ثم تطابق هوية المرسل الموقعة مع الربط
المحفوظ. الهوية المحجوبة مرفوضة. لا fallback إلى بحث الهاتف/الاسم، ولا إنشاء أو ربط أثناء GET.
إذا أنشأ الوكيل معرّف محادثة جديداً فعليه capture موثوق أولاً لربطه بالهوية نفسها؛ انقضاء سياق النموذج لا يمحو
الربط الدائم ولا يتطلب إعادة سؤال بيانات العميل.

داخل المعاملة تعاد قراءة صلاحية المفتاح تحت FOR SHARE، ثم يؤخذ قفل الهوية بترتيب الكتابة نفسه. الملف يقرأ
تحت FOR SHARE ليكون الإصدار والقيم ودليلها متسقين بالنسبة لتصحيح أو تحديث متزامن. سحب الصلاحية المتقدم على
المعاملة يرفض القراءة؛ السحب المتسابق بعدها ينتظر انتهاء القراءة بدلاً من تسريب حالة مختلطة.

## الرد 200

`schemaVersion, profileId, profileVersion, fields, missing, needsReview, followUp` فقط.
`Cache-Control: no-store`؛ على الوكيل منع رد قديم من استبدال نسخة أحدث في حالته.

كل من `name, phone, residenceCityId, address` داخل fields يعيد:

- `value`: القيمة الحالية المقبولة، أو null. الهاتف غير مطلوب لتليغرام.
- `source`: دليل الحقل المطابق **لهذه القيمة** والمطبّق فعلاً: CUSTOMER_STATEMENT أو WHATSAPP_SENDER أو
  TELEGRAM_OWN_CONTACT؛ وإلا UNRECORDED، أو null للحقل الفارغ.
- `verification`: MISSING للفارغ، UNKNOWN عندما لا يوجد مصدر مطابق مثبت، UNVERIFIED للإفادة الصريحة التي
  لم تثبت مستقلاً، CHANNEL_VERIFIED للهاتف فقط عند اجتماع دليل القناة المطابق وعلامة التوثيق الحالية.
- `observedAt`: وقت الدليل المطابق، لا وقت GET ولا وقت اقتراح مرفوض. null عند غياب الدليل.

لا تعاد اقتراحات معلقة أو مرفوضة، ولا المرشحون أو الأدلة الخام أو سياق المحادثة أو حسابات الفروع أو
الشحنات/الفواتير. `needsReview` يبيّن نزاع حقول ملف مرتبط؛ تعاد القيم الحالية المقبولة فقط ولا يتجاوز ذلك
بوابة مراجعة الحجز. `missing` يشمل الحقول الأربعة الفارغة وصفياً؛ ليس شرط اكتمال حجز ولا طلب هاتف إجباري.

المتابعة تعيد الفرع الحالي وحالة ASSIGNED / UNASSIGNED / NEEDS_REVIEW. عند وجود علامة مراجعة تعيد
`reason=REVIEW_REQUIRED` مع الاحتفاظ بالفرع السابق إن وجد؛ السبب هنا حالة **حالية** عامة، لا ادعاء إعادة
تقييم قواعد التوجيه. عند غياب الإقامة والمتابعة تعيد NO_RESIDENCE؛ وإلا reason=null.

## تصحيح الموظف والمصدر غير المسجل

المصدر ليس تخميناً لآخر كاتب. بعد تصحيح قيمة في CustomerProfile، تعرض القراءة القيمة والإصدار الجديدين؛
إن لم يسجل الكاتب دليلاً مطابقاً للحقل فلا ترث القراءة دليل القيمة السابقة ولا توثيقها، بل UNRECORDED / UNKNOWN.
وجود قرار ربط بشري أو بيانات قديمة وحده لا يثبت الاسم أو الهاتف الجديدين. لا تستنتج STAFF_VERIFIED من مجرد
سجل مراجعة أو علامة phoneVerified لا يساندها دليل القيمة الحالية.

هذا PR لا يضيف مسار تعديل موظف أو يزامن تعديلات حساب Customer في فرع إلى CustomerProfile تلقائياً.
اختبار التصحيح يحاكي كتابة ملف موظف ملتزمة ومعها سجل تدقيق، ويثبت قراءة النسخة الحالية وعدم استعارة
المصدر القديم. رفض الموظف للاقتراحات يختبر كذلك عبر المسار الفعلي في #155.

## الأخطاء

| HTTP / code                                                  | المعنى                                                                  |
| ------------------------------------------------------------ | ----------------------------------------------------------------------- |
| 400 INVALID_INPUT                                            | query ناقص أو غير صالح أو يحمل اختيار عميل/شركة إضافياً                 |
| 401 INVALID_CHANNEL_ASSERTION                                | غلاف غير صالح/منتهٍ أو طلب عُدّل بعد التوقيع                            |
| 401/403 من حارس المفتاح، أو 403 SCOPE_REQUIRED داخل المعاملة | مفتاح غير صالح/ملغى أو صلاحية سُحبت                                     |
| 403 CHANNEL_NOT_ALLOWED                                      | حساب القناة غير مسموح لهذا المفتاح                                      |
| 404 PROFILE_NOT_BOUND                                        | لا ربط بهذه المحادثة/المفتاح/الشركة/المرسل، أو الهوية محجوبة؛ الرد واحد |
| 409 IDENTITY_REVIEW_REQUIRED                                 | الهوية نفسها غير محسومة وليس لها ملف مرتبط؛ لا معرفات مرشحين أو pending |
| 503 CUSTOMER_CAPTURE_UNAVAILABLE                             | المفتاح الأساسي مغلق أو خطأ تخزين مؤقت؛ لا ادعاء نجاح                   |

أخطاء التحقق لا تعيد بيانات مرشحين، والقراءة لا تمنح nolct_ أو تتبع معاملات. لا تتغير نتيجة عملية capture
الأصلية عند استرجاعها؛ self هو الطريق المنفصل للحالة الحالية.

## التحقق والتسليم

اختبارات HTTP على PostgreSQL تغطي: تليغرام بلا هاتف، تحديثات لاحقة، اقتراحاً مرفوضاً ورفض موظف فعلياً، تصحيح
قيمة دون دليل مطابق، هاتف قناة موثق ثم تغير قيمته، عزل المرسل/الشركة/المفتاح/المحادثة، الهوية المحجوبة،
المطابقة الملتبسة، سحب المفتاح والصلاحية بين guard والمعاملة، وعدم إنشاء حالة أو منح قراءة معاملات.
اختبار التوقيع يثبت شمول conversationId في query، والعقد يرفض محددات النموذج الإضافية.

اختبار الطرفين يكون على SHA هذا PR وSHA محدد من erp-agents، مع مفاتيح اصطناعية وقاعدة محلية فقط.
لا دمج أو نشر أو فتح مفاتيح التشغيل بهذا التسليم. يظل #155 وترحيلاته وموافقته بوابة سابقة مستقلة.
